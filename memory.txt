    Each account runs two things, and the chat mode controls what text both of them send:

    text

    Inbox responder (runCycle → processDMAutoResponses): accepts friend requests, sends a first message to new DMs, and replies to unread messages.

        Single Sequence (chat_mode = "single", the default)

        Settings: "Message sequence (Single)" text box. Each line is one step: line 1 is the opener, line 2 is the reply to their first message, and so on. Lines can use {a|b} or [a|b] random choices and %username%.
        How it works: the text becomes cfg.AvailableSequences = [[lines…]]. Each message the person sends moves the bot one line forward (SentMessageCounts[userID]).
        In the inbox, once the lines run out, later messages are marked seen and get no reply.
        In match chat, it sends a line, waits for a reply ("Skip timeout"), sends the next line, and so on. After the last line it waits up to 5 minutes for the chat to close, then moves on.

        Folder Sequences ("folder")

        Settings: Load Folder opens a folder picker and reads every .txt file in it as a separate sequence (LoadMessageFolder). Clean Loaded clears them. A status line shows how many were loaded.
        How it works: cfg.AvailableSequences holds every loaded file. getActiveSequence picks a random one that still has a line at the current step. It picks again at every step, so one conversation can mix lines from different files. If nothing is loaded, it falls back to the Single text.

        Keyword Based ("keyword")

        Settings: Load Keyword File (a .txt file, checked by ParseKeywordRules). Clean Rules clears them and switches back to Single. Open Unmatched Log opens data/unmatched_keywords.txt in Notepad. There's also an editable rules text box where each line is (kw1|kw2|phrase){reply template}, and a "N rules active" counter.
        How it works:
        Opener: always the reply template of rule #1. In match chat it falls back to "hey" if that's empty.
        Matching (MatchKeyword): single words must match as whole words; phrases (anything with a space or punctuation) are matched as substrings. Rules are checked top to bottom.
        Inbox: each unread message gets the first matching rule. If nothing matches, the message is logged to the unmatched file and gets no reply.
        Match chat: it prefers rules not yet used in that conversation, and reuses one only if every match has been used. If nothing matches, it logs the message, adds 1 to the Skip counter, and drops that user.

    What it is: "ChitChat Bot", a Windows desktop app plus a command-line bot that automate accounts on app.chitchat.gg. It logs in through a real Chromium browser and saves the session. Then it accepts incoming friend requests, sends a first message to new DM conversations and auto-replies to incoming messages, using keyword rules or saved message templates. It can run several accounts at once, each through its own rotating proxy.

    Technologies

    text

    Go 1.25 (module chitchatbot), about 8.8k lines including tests
    Wails v2: the desktop UI framework, running in a WebView2 window
    Frontend: plain HTML, CSS and JavaScript in frontend/dist, with no framework or bundler
    Browser automation: go-rod and chromedp (you choose one); a bundled Chrome for Testing build means users don't need Chrome installed
    Storage: BadgerDB for the app's settings and logs; JSON files for each account's state
    Networking: gorilla/websocket for live updates, utls to make its connections look like Chrome's, HTTP and SOCKS5 proxy rotation
    Licensing: a hardware-bound key checked against license-api.nilhasancl.workers.dev
    Build: a PowerShell bundle script; Windows x64 only

    Folders (inside go_erp/)

    text

    main.go, app.go: the desktop app's entry point and the backend the UI calls (start/stop, settings, proxies, running several browsers)
    cmd/chitchatbot/: command-line entry point (flags for backend, profile, headless)
    cmd/chitchatui/: a second copy of the desktop entry point, plus frontend/ (dist/ and generated wailsjs/ bindings)
    internal/bot/: the core logic. Polling and live-message loop, friend accepts, DM sending with typing indicators and random delays, keyword replies, and a shared registry so several accounts don't message the same user
    internal/api/: HTTP client for api.chitchat.gg
    internal/browser/: the rod and chromedp backends, plus injected scripts
    internal/proxy/, internal/workerplan/: proxy parsing and rotation, and matching accounts to proxies
    internal/uistore/, internal/store/: Badger and JSON storage
    internal/license/, internal/runtimeassets/, internal/model/: license check, finding the bundled browser and WebView2, data types
    scripts/bundle-windows.ps1: builds both executables and bundles the WebView2 and Chromium runtimes
    data/: runtime state (profiles, registry, flagged users, Badger database)
    sms/, sss/: message text files the bot can load
    build/, dist/, release/, *.exe: build output and downloaded runtimes, about 1.6 GB

EVAChat Flow — analysis, plan and locked scope
Goal

Replace the dashboard's third mode, Keyword Based, with EVAChat Flow in the v1.0.0 ChitChat Bot source. The first two modes — Single Sequence and Folder Sequences — remain unchanged.

This plan covers the active, build-used UI and runtime path only. No browser-login, API client, proxy, account, registry, transport, or unrelated dashboard code will be changed.

    Safety boundary: the replacement will be a consent-aware, age-gated conversation flow. It will not include explicit sexual scripts, contact-harvesting, account-evasion, or forced/unsolicited messaging logic. Default replies will be neutral and editable by the project owner.

What I verified in the target release

The GitHub release contains go_erp.zip (about 1.29 GB). The actual Wails build uses:

    root main.go and root app.go
    embedded dashboard assets under cmd/chitchatui/frontend/dist/
    wails.json, which points Wails at that cmd/chitchatui/frontend directory
    Go bot runtime in internal/bot/

cmd/chitchatui/app.go is a second, unused copy for the normal wails build path. It is out of scope.
Current keyword-mode route

    Dashboard radio option: cmd/chitchatui/frontend/dist/index.html
    Dashboard state/actions: cmd/chitchatui/frontend/dist/app.js
    Saved UI settings: internal/model/ui.go and internal/uistore/store.go

    Match-chat replies: internal/bot/logic.go → executeMatchChatSequence() → executeMatchKeywordChatSequence()

Therefore changing only the dashboard label would be incomplete. The runtime's opener, inbox reply, and match-chat reply paths must all call the same EVAChat Flow engine.
Important finding about the EVA source

The EVA repository has two engines:

    Default: eva_flow.py, driven by data/input/ + data/output/ and a stage machine.
    Legacy: chat/rules.py, plus Python-specific local_db/, stage_rules/*.json, style/persona code, and TgBrain fallback.

The default EVA flow does not use local_db/ or the stage-rule JSON files for normal replies. Copying those files into the Go project without also porting the old Python legacy engine would add data that is never executed.

Implementation decision: EVAChat Flow v1 will port the active/default input/output stage engine to native Go. It will use an editable TXT dataset. The Python-only legacy engine, unused local_db, and stage JSON rules are deliberately excluded from this replacement scope.

Native Go engine behavior

EVAChatEngine will have per-conversation state and will return a structured result:

Go

type EVAReplyResult struct {
    Text       string
    SourcePool string
    Ended      bool
    Reason     string
}

It will provide the same engine behavior everywhere:

    initial message / greeting handling
    stages: NEW → WAIT_AGE_GENDER → WAIT_COUNTRY → MIDDLE → END
    matching: exact → punctuation-normalized → whole-word substring → slang-normalized → token-subset
    country and age/gender extraction
    pool-level and line-level no-repeat behavior
    configurable reply cap and a neutral closing response
    persisted conversation state so it survives the next polling cycle
    safe failure: missing or malformed optional files cause a clear log and a neutral fallback; the worker does not panic

The old KeywordRule, ParseKeywordRules, and unmatched_keywords.txt implementation will no longer be called by the dashboard's third mode. It can remain in the source untouched as inactive legacy code, avoiding unrelated deletion risk.
State persistence

The existing data/profiles/<profile>/bot_state.json will receive a new eva_chat_sessions map inside each account state. It will store only the state necessary to continue the conversation: stage, captured non-sensitive flow facts, reply count, used pools/lines, and ended status. No source changes to browser sessions, API calls, or registry behavior are needed.
Unified runtime adapter

A small helper in internal/bot/logic.go will call the engine for three entry points:

    new inbox DM opener
    normal inbox reply
    matched-chat opener and replies

This is required because the existing code has separate keyword branches in all three places. The adapter prevents behavior drift between inbox and match chat.

import (
	"embed"
	"fmt"
	"io/fs"
	"os"
	"path/filepath"
	"strings"
)

// evaAssets is a small, neutral starter pack. It is copied only when a file
// does not already exist in data/eva_chat, so user edits are never overwritten.
//
//go:embed eva_assets/README.txt eva_assets/countries.txt eva_assets/input/*.txt eva_assets/output/*.txt
var evaAssets embed.FS

// EnsureEVAChatData creates the editable EVAChat Flow data directory when it
// is absent and returns its absolute runtime path.
func EnsureEVAChatData(dataDir string) (string, error) {
	root := filepath.Join(dataDir, "eva_chat")
	if err := os.MkdirAll(root, 0o755); err != nil {
		return "", fmt.Errorf("create EVAChat data directory: %w", err)
	}

	err := fs.WalkDir(evaAssets, "eva_assets", func(assetPath string, entry fs.DirEntry, walkErr error) error {
		if walkErr != nil {
			return walkErr
		}
		if assetPath == "eva_assets" {
			return nil
		}

		rel := strings.TrimPrefix(assetPath, "eva_assets/")
		destination := filepath.Join(root, filepath.FromSlash(rel))
		if entry.IsDir() {
			return os.MkdirAll(destination, 0o755)
		}
		if _, err := os.Stat(destination); err == nil {
			return nil
		} else if !os.IsNotExist(err) {
			return err
		}

		data, err := evaAssets.ReadFile(assetPath)
		if err != nil {
			return err
		}
		if err := os.MkdirAll(filepath.Dir(destination), 0o755); err != nil {
			return err
		}
		return os.WriteFile(destination, data, 0o644)
	})
	if err != nil {
		return "", fmt.Errorf("bootstrap EVAChat starter data: %w", err)
	}
	return root, nil
}
